# Reproduction and diagnosis

Use this loop with the affected stack's commands and the [behavioral testing guidelines](testing.md) when writing a reproduction or regression test. Redact credentials and private data in commands, fixtures, logs, and captured traces. Read relevant domain invariants and architecture decisions first.

1. **Establish a sharp failing signal.** Run a focused command that exercises the reported symptom and asserts its exact result. Prefer a unit/widget/handler test, CLI fixture, endpoint request with assertions, rules emulator test, or replay of a captured event. Use a measured benchmark/profile for performance regressions. Record the command and actual failure before modifying production code. If unavailable hardware, access, or environment prevents reproduction, gather bounded evidence, identify the limitation, and avoid claiming a verified cause.
2. **Reproduce and minimize.** Confirm this is the reported failure. Remove inputs/dependencies one at a time while rerunning the check. For races, use controlled synchronization or a measured repeatable stress loop; arbitrary sleeps are weak evidence. Use bisection when history identifies a useful regression range.
3. **Rank falsifiable hypotheses.** For uncertain causes, compare plausible explanations and predict what one controlled change would do. Use three to five candidates for a hard ambiguous bug; skip manufactured alternatives when the cause is already established by evidence, and explain that decision.
4. **Probe one prediction at a time.** Add narrowly scoped, uniquely tagged diagnostics or a targeted experiment. Profile instead of adding verbose logging to a performance-sensitive path. Remove temporary instrumentation afterward.
5. **Fix at the correct seam.** Preserve a behavioral regression check that fails before the fix and passes after it. Change the smallest complete cause, then rerun both the minimized check and original scenario. Test real caller behavior rather than private implementation. Broaden verification when shared contracts change.
6. **Clean up and report.** Remove tagged logs, synthetic temporary data, and throwaway harnesses; preserve user-owned artifacts. Report root cause, confirming evidence, regression check, original scenario outcome, and remaining verification gaps.

Runtime choices: Go uses focused package/handler/integration tests, `httptest`, and synchronized race/cancellation reproductions; Rust uses Cargo tests and controlled async coordination; Flutter uses unit/widget/integration tests; Dart Frog uses handler tests or an asserted request; Astro/Next.js uses component/browser/route tests, build or production-preview reproductions, and framework diagnostics; Firebase uses client-context rules/emulator tests or a minimal service event; DevOps reproduces the actual failing build/stage/container. Use structured human-assisted steps only when automation cannot exercise the symptom. Do not replace a Go, Rust, or infrastructure reproduction with Dart-specific tooling.
