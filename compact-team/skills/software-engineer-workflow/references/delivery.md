# Delivery and correction loop

Use for multi-step implementation, authorized fixes following review/QA, or recurring verification failures. Keep small work lightweight. This procedure runs within the compact engineer; it does not require a specialist persona, another agent, or team helper scripts.

## Delegated delivery boundaries

When delegated, follow the task packet's delivery role and exact targets. **Implementation** includes the authorized branch, verification, self-review, commit/push, PR creation, and existing card transitions. **Review** keeps the repository read-only and returns findings and a score; it does not apply fixes or post a remote approval. **Correction** continues the same implementation branch, PR, and card, resolves the supplied findings or evidence gaps, and returns updated revisions and validation. Never start a new branch from base or duplicate the PR for a correction. Honor a narrower user scope or explicit opt-out, and report missing destinations or access without inventing them.

The coordinator owns the fresh-worker sequence and maintains at most one active child at a time. Workers do not dispatch the next reviewer or correction. For orchestrated PR delivery, there are at most **three independent scored reviews total** and **two correction assignments** between them. Stop at an independent **5/5**. A score below 5/5 in rounds 1 or 2 requires a coordinator-assigned correction followed by a fresh reviewer. If round 3 remains below 5/5, return remaining findings and stop; do not begin a fourth review or an unreviewed final correction. Self-review does not count as an independent scored round. Preserve the coordinator's ledger across sessions; workers cannot reset it or start another cycle.

The steps below guide work within the current assignment and do not authorize another review/correction round. Return the actual PR/head, card state, finding dispositions, checks, and unresolved gaps for the coordinator's next decision. A favorable recommendation at 4/5 does not pass the orchestrator's 5/5 gate. No score authorizes merging, deployment, issue closure, or marking the card Done.

For authorized PR delivery tied to an existing board task, complete and verify the [PR/task association](pr-standards.md#link-the-pr-to-the-board-task) before reporting delivery complete. Return evidence of the task link in the PR and the PR link on the task, plus the observed native relationship when supported. Corrections retain the same association; a failed link remains an explicit incomplete delivery step.

## Carry the task through completion

1. **Establish the slice:** Carry forward agreed scope, acceptance criteria, domain invariants, affected contracts, and relevant product/design assets. Reuse existing discovery. If a material product choice remains unresolved, identify it and continue independent work; do not silently decide a new business requirement.
2. **Implement and verify:** Work in cohesive, independently verifiable slices. Follow the selected stack and [behavioral testing](testing.md) guidance; retain reproduction/regression evidence for fixes. Run focused checks while editing, then required broader checks for affected consumers.
3. **Review the result:** Inspect the final diff using the [review procedure](review.md). Include QA evidence when relevant. Identify actionable standards/spec findings and verification gaps against the pinned target. Keep self-review separate from any independent review the project requires.
4. **Resolve authorized findings:** For each actionable item, retain its location, trigger, expected behavior, evidence, and proportionate correction. Track whether it is fixed, remains unresolved, or was rejected with a supported reason. Fix the cause, rerun the failing scenario, and check affected consumers; do not change acceptance criteria or tests merely to make the feedback disappear.
5. **Re-review affected behavior:** Inspect the revised diff and update the evidence after fixes. Re-run checks invalidated by the change; preserve still-applicable results rather than repeating unrelated suites. Address new findings within the current authorized scope; delegated workers return unresolved findings for the coordinator's next decision within its round limit. A review-only request reports findings and stops without modifying the target.
6. **Report actual completion:** Complete when the requested behavior, required checks, and applicable review conditions are satisfied, or state exactly what remains unverified or blocked. Use [PR standards](pr-standards.md) for PR preparation. Keep publication, merge, deployment, board transitions, and issue closure tied to their actual authorized scope and observed state.

For larger work, use a concise task list or existing issue tracker to retain per-slice criteria, status, latest revision, evidence, findings, and next action. Do not require a new tracking document for a small fix. For mixed product/engineering work, carry the same contracts and evidence across the role transition rather than restarting the task. Use the project's existing board states when board updates are authorized; do not infer Done or issue closure from an implementation claim.

## Checkpoints and interruption recovery

For a long or multi-step assignment, use the coordinator's supplied writable scratch checkpoint/handoff path or an existing suitable artifact. Keep it outside the repository/review target when a review must be read-only, and do not commit scratch evidence or require a new file for a tiny task. Report an unavailable recovery destination. Keep updates concise and replace the checkpoint atomically when supported so interruption does not destroy the previous usable evidence.

Record the assignment label and role, workspace, branch/base and latest known revision, supplied review round, completed/unfinished criteria, changed files, actual check results and applicable revisions, artifact/PR/card URLs and observed state, and the next action. Distinguish verified observations from pending or uncertain effects. Before an external mutation, record its intent and target; afterward record its actual result. If a crash occurs between success and recording, the pending entry requires checking the real destination before retrying. Never put secrets or raw sensitive logs in a checkpoint.

Update at meaningful milestones such as an implemented slice, completed validation, or observed publication. A worker cannot guarantee timed updates during model generation or a blocking tool; runtime activity reporting is separate. Do not write invented progress. Save the final evidence-backed handoff before returning it to the coordinator; the artifact provides recovery if tool output is capped. Its existence does not establish process exit, successful checks, or task completion by itself.

When assigned a continuation after confirmed process exit, read the prior evidence and inspect the actual workspace/revisions and authorized remote targets. Preserve others' changes and completed task work. Resolve uncertain operations before retrying; continue on the same implementation branch/PR and card, retaining the coordinator's review-round ledger. Implement only unfinished steps and rerun only checks invalidated by subsequent changes. Report any discrepancy or unavailable verification. Interruption does not authorize repeating publication, creating another implementation branch or PR, restarting the review limit, changing model settings, or weakening acceptance criteria.

## When corrections keep failing

If the same defect or structural problem survives successive correction/review passes, stop applying the same class of patch. Recheck the original reproduction, assumptions, dependency/environment differences, ownership, seam, and domain rules. A smaller fix that repeatedly breaks another caller can indicate the wrong boundary or an incomplete contract.

After two unsuccessful corrections based on the same assumption fail the same check, state that shared assumption and the observed failures in the task evidence. Before another patch, run a focused experiment that could disprove the assumption, with a predicted distinguishing result; use the [diagnosis loop](diagnosis.md) when needed. Revise the assumption or choose the next correction from the observed result. Unrelated failures or an unavailable tool do not by themselves disprove a design premise. If the experiment cannot run, state the missing evidence and continue only work that does not depend on the unresolved assumption.

This diagnostic guidance does not extend the coordinator's review/correction budget or authorize another patch after its stop condition. Report the experiment needed and remaining evidence gaps when further work falls outside the current assignment or permitted rounds.

Summarize the recurring failure and attempted corrections with evidence. Revisit viable interface designs using [design guidance](design.md). For systemic coupling, scattered changes, or cycles, propose a scoped [architecture audit](architecture-audit.md) and perform it when within the authorized work. Repeated structural failures warrant this consideration even when they occur in fewer than three modules; a numerical smell count is not the only trigger.

When an agreed correction establishes a lasting module boundary, consider an executable architecture check such as an existing import rule, dependency-cycle check, or public-contract test to prevent recurrence. Add only checks that enforce a real contract within scope; do not pin file layouts or instruction prose to a test.

If the correction requires a product decision or a larger migration outside the task, present the concrete decision and its trade-off with the affected evidence. Do not expand into an unrequested redesign, retry cloud operations speculatively, or keep an unbounded fix/review loop running. Report a genuine external blocker with its next action; difficult but actionable local work remains work to complete.

## Handoff

Lead with changed behavior and files, then material decisions, acceptance/regression evidence, review findings resolved or remaining, required checks and outcomes, and the next action when incomplete. For delegated PR delivery, include the delivery role, supplied review round, branch/base, actual PR URL and head SHA, card/board identifiers and observed state, and stable finding IDs with dispositions. Reviewers include the reviewed SHA, whole-number score, explanation, and recommendation; correction workers do not award themselves an independent score. State external delivery status when relevant. A pending job, a locally passing test, a clean self-review, and human approval are different states. Do not claim a sign-off or publication that did not occur.
