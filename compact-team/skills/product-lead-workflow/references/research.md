# Research and evidence

## Investigate

Frame the question, decision it informs, relevant scope, and missing evidence. Answer a clear request directly; restate intent only when it resolves ambiguity. Inspect provided material and local code/docs first when they can establish the facts.

Search when information is unknown, uncertain, time-sensitive, or explicitly requested. Use focused queries and sources appropriate to the claim: official documentation/releases for APIs and versions, source repositories and tests for implementation, original studies or authoritative data for empirical claims. Check publication date, event date, version, population, and context before applying a result. Existing documents may describe plans rather than shipped behavior.

Fetch and read the relevant source content; search snippets alone do not establish complex claims. Trace code behavior through relevant callers, configuration, tests, and dependencies. Distinguish what source code suggests from behavior actually exercised. Read-only investigation does not require changing production code or data.

Cross-check material claims with independent sources where practical. Two pages repeating the same announcement are not independent corroboration. Resolve conflicting evidence by source authority, directness, dates, methodology, and applicability; explain unresolved disagreement rather than averaging it away.

## Synthesize and review

Separate verified facts, reasoned inferences, assumptions, and unknowns. Never invent citations, quotes, usage metrics, interviews, experiments, or tool results. If access is unavailable, identify the missing evidence and continue with supported conclusions. Protect private source material; do not upload code, documents, or personal data to external services without scope authorization.

For comparisons, use criteria derived from the user's needs and explain trade-offs. Avoid invented precision, unsupported rankings, or selecting an option merely because it is familiar. Stop searching when the question is answered with sufficient evidence; additional research should resolve a material uncertainty.

Before delivery, check that each consequential claim is supported, sources apply to the relevant version/context, contrary evidence is considered, and conclusions answer the original question. A recommendation should identify what would change it and what remains unverified. A research conclusion may establish constraints, but it does not silently authorize product scope or external actions.

Lead with the answer and connect the evidence to the decision. Cite web claims near the supporting statement using direct page links; use precise local file references for code findings. Include a compact source list when it helps reuse; avoid dumping every visited URL. Use short compliant quotations only when necessary. State temporal/version limits when they affect the conclusion.

When research feeds a spec or backlog, carry forward relevant constraints, source links, confidence limits, and unanswered product choices. Do not convert an inference into an acceptance criterion without identifying it as a proposed decision.
